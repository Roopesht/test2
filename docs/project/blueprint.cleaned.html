🤰 Maternal Care Platform

Multi-Tenant PaaS/SaaS for Hospital Antenatal, Labour Room & Delivery Management

Tagline: Customisation · Antenatal · LR · Summing Engine · In-App Chat · Delivery Archive

Source note: This blueprint is reconstructed from an unstructured internal notes dump ("48. Changes (complete)"). Wherever the source was ambiguous, contradictory, or literally posed as an unanswered question, it is called out in the Open Decisions section rather than silently invented.

📋 System Overview

▼

A multi-tenant platform that lets hospitals manage the full maternity journey — antenatal registration, labour room (LR) workflow, delivery/admission, billing, and patient archival — under a single, standardised paid-tier product with minimal manual hand-holding. Each hospital (tenant) configures its own departments, packages, and rate lists; a platform-level Super Admin governs onboarding, cross-tenant audit, and usage billing.

🤰 Antenatal-to-Discharge

Covers registration, EDD arbitration, labour room gating, delivery/admission, and discharge receipt as the final document.

🧮 Summing Engine

Central charge aggregator across 4 delivery categories and 2 rate lists, with package caps and override handling.

🏢 Multi-Tenant Configuration

Hospital Admin owns all configuration — departments, staff, rate lists, branding. Identical whether the tenant is on PaaS or SaaS.

🗃️ Delivery Archive

Natural vs. Forced archive paths with strict ACTIVE ↔ ARCHIVED status transitions and a defined protocol.

💬 In-App Chat

Scoped strictly to Patient ↔ RMO/Lady Doctor ↔ Hospital Admin, and only while the patient is ACTIVE.

🪙 Coin-Based Subscription

Every chargeable transaction consumes coins (50 per registration entry); pricing has a defined discount floor above 10,000 coins.

Key Stakeholders & Users:
  • Super Admin — Platform-level; ratifies hospital onboarding, runs cross-hospital override audits, tracks usage/API-cost billing
  • Hospital Admin — Owns all tenant configuration: departments, packages, rate lists, staff, branding
  • USG Staff / Lady Doctor — Only roles permitted to register a patient and set EDD
  • LR Staff — Unlocks Gate 1, flags LSCS/NICU, overrides delivery charges (if present in rate list)
  • Billing Reception — Adds/overrides charges once the patient is past Gate 1
  • RMO, Incident Manager — Clinical support and always-on escalation
  • Patient — Self-service search, chat access while ACTIVE only

Registration Flow

  • Onboarding begins when a hospital starts registration; a government certificate/receipt proving the hospital's existence must be uploaded.
  • Upload grants temporary approval immediately; an offline Super Admin later ratifies the hospital or stops the service if the document doesn't validate.
  • The "250k" initialization step (see Subscription & Coin Economy) is also part of hospital onboarding.
  • Header and footer branding must be uploaded before the hospital can proceed with example/sample configuration.

Departments

Each hospital decides which departments are present, independently: USG, Lab, NICU, LSCS, RMO, Lady Doctor, LR Staff, Billing Reception. Any combination — including none — is allowed at setup, but once decided, the selection is locked (not changeable later).

🔀 PaaS → SaaS Model

▼

Configuration is identical whether a hospital is on PaaS or SaaS — Hospital Admin owns all configuration either way. SaaS adds exactly four differentiators on top of the PaaS base:

®️ Trademark Registration

Significant independence via the hospital's own registered trademark (assisted, 3-step document process; 2-step follow-up).

📱 Own Signature App

Hospital gets its own branded app rather than operating inside the shared platform app.

🏪 Direct Store Listing

Direct Play Store / Apple Store presence (own developer listing), not bundled under the platform's account.

🖥️ Self Server Hosting

Option to self-host rather than run on shared platform infrastructure.

An automated procedure is planned for Play Store / App Store submission; the hospital supplies its own branded APK for submission. Exact submission tooling is still pending (see Open Decisions).

📅 Antenatal & EDD Arbitration

▼

EDD (Expected Date of Delivery) is initially set by LMP and cross-checked/arbitrated by USG.

Contradiction in source notes: one passage states ANC registration "can be done by either USG staff or Lady doctor" (Lady Doctor registering by reviewing a prior report); another states that because EDD calculation is USG's exclusive prerogative, "registration cannot be done by another department" — only USG registers, and other departments may only add charges afterward. These two statements conflict on whether Lady Doctor can register a patient. Needs a decision before this is built.
Gestational AgeAllowed EDD Tolerance
Up to 34 weeks± 2 weeks (e.g., LMP EDD of 28.09.26 must fall between 15.09.26 and 11.10.26)
34–35 weeks± 3 weeks
36 weeks onward± 4 weeks
Freeze rule: if a patient is scanned multiple times across these windows (<34, 34–35, >35 weeks), the earliest EDD value is taken, frozen, and never recalculated afterward.

🚦 Gate Flow

▼
graph LR REG["Registration\n(EDD set by USG)"] --> G1["Gate 1\n(formerly 'Gate 2')\nUnlocked by LR Staff"] G1 -->|Natural path| G2["Gate 2\n(Natural Archive track)"] REG -->|"EDD + 1 month, no-show"| G3["Gate 3\n(Forced Archive track)"] G1 -.crossing disables.-> G3 G2 --> NA["Natural Archive"] G3 --> FA["Forced Archive"]
  • There is no "Gate 0" — that stage is already covered by registration/EDD.
  • G1 and G2 relate to the Natural Archive path; G3 relates to the Forced Archive path.
  • Forced archive triggers one month after EDD expiry with no patient show — the patient can still come in at any point during that one-month window (e.g., on the last day of expiry).
  • If G1 has already been crossed, G3 (forced archive) is disabled.
  • Once past Gate 1, the workflow becomes a simple hospital service: charges are added and the package limit applies (LR Room/NICU staff aren't separately gated here, since there's no inter-service summation or package discount beyond the configured/overridden amount).

🧮 Summing Engine & Charges

▼

The Summing Engine aggregates charges across 4 delivery categories and 2 rate lists, and is the arbiter of the package cap concept (applies only to Normal Delivery). The discharge receipt is the final document once summing is complete.

CategoryAmount TypeNotes
Normal DeliveryProper amountSubject to summing engine; package cap stops standard charges at the declared limit
Abnormal DeliveryToken amount~30% of deliveries; normal package logic doesn't apply, so charge bounce is expected (e.g., ₹12,000 → ₹15,000) for complications like breech, face presentation, oxygen, blood transfusion, vacuum-assist, or extended delivery time
LSCSToken amount~50% of Abnormal Delivery cases escalate to LSCS (≈15% of all deliveries are neither Normal nor LSCS outright — they pass through Abnormal first). Example configuration from source: LSCS adds ₹20,000 on top of the ₹12,000 Normal Delivery (ND) base.
NICUToken amountCan attach on top of Normal, Abnormal, or LSCS — a 4th, independent situation. Example configuration from source: NICU adds ₹25,000 besides the ₹12,000 ND base.

These per-category amounts are LR Staff-configured at the point delivery is confirmed (as soon as LSCS and/or NICU is flagged, the corresponding add-on charge is applied) — this is also why there's no separate "LSCS Room staff" or "NICU staff" role: there's no inter-service summation or package discount at that stage, only the configured amount or an override.

💬 Chat & Notifications

▼

In-App Chat

  • Participants limited strictly to: Patient ↔ RMO/Lady Doctor ↔ Hospital Admin.
  • ANC staff cannot chat, except the Lady Doctor (special handling when more than one is assigned).
  • Billing Reception has no in-app chat access.
  • Chat is available only while the patient is ACTIVE; it is removed on archive.

Notification Service

  • Weekly and monthly SMS reports are sent to Hospital Admin via the Notification Service.
  • On-call alerting uses AWS SNS directly — no third-party paging tool required.

🔍 Reconciliation & Overrides

▼
Preserve-all-entries policy: wrong entries and overridden entries are never deleted — they are preserved permanently. This full history enables staff appraisals and a reprimand flow that assigns accountability.
  • Manual overrides can also be performed by Billing Reception (equivalent to LR Staff rights) once past Gate 1; the 90-day cooldown no longer applies at that point.
  • Override audit reports are available to Super Admin across all hospitals.
  • Super Admin can view usage breakdown — API calls weighted by operation cost — per hospital, for platform-level billing/capacity insight.

🏢 Multi-Tenancy & Feature Flags

▼
Feature flags: because this is a multi-tenant application, feature flags are needed to track which app version is "live" and which client (hospital) is running which version — important for staged rollouts and version-specific support.

❓ Open Decisions

▼

Items the source notes raised as literal open questions, or left genuinely ambiguous, rather than as decided specification:

Unresolved items:
  • 250k threshold behaviour — the notes ask outright "after 250k what all will happen" without an answer. Needs a product decision (revenue milestone? coin-purchase milestone? registration count?).
  • Registration contradiction — whether Lady Doctor (in addition to USG) can perform initial patient/ANC registration is stated both ways in the source (see EDD Arbitration).
  • Departments vs. staff roles grouping — unclear whether USG/Lab/NICU/LSCS/RMO and Lady Doctor/LR Staff/Billing Reception are meant as one configurable list or two groups with different rules (see Onboarding).
  • "First service to be defined" — the notes flag that the first service in the transaction/charge sequence still needs to be decided.
  • "Points" vs. "coins" — the Subscription Service is described as deducting "50 points" per registration entry, while a separate passage on transactions says "50 coins per service." These may be the same unit described inconsistently, or two different units — needs reconciling; this blueprint treats them as one unit ("coins").
  • OPD rate list — explicitly noted as needing configuration; no rate list currently exists for OPD.
  • Play Store / App Store automation — "give some more flows for server configuration" and "we have to give some APK to him so that apply them" suggest the submission automation is still being designed, not finalized.
  • Trademark "Act" — the notes mention "Act will there" in the context of trademark registration steps, with no further detail on which Act or how it applies.
  • "Sign up vs Sign in" — listed as a heading in the source with no elaboration; likely meant to distinguish hospital self-registration from routine user login, but not detailed.
  • "N-chain" / "N-Loggers" — both terms appear in the source's role-flow notes without definition. Possibly shorthand for an audit/logging role or a chain-of-custody concept — not enough context to resolve confidently.
  • Header/footer upload timing — noted as required "before saying go ahead with examples," implying example/sample data flows aren't finalized either.
  • Forced-archive patient-count scenario (the month-by-month 10/300/550/750/1000-patient walkthrough, shown in Archive Architecture) reads as an illustrative example of volume growth over 11 months rather than a hard specification — worth confirming with the source author before building capacity assumptions on it.
  • "System Highlights" section intentionally omitted — the source itself flags this section as a restated summary of already-covered material and instructs that it can be removed if it reads as duplication to an AI/agent audience, which is the case here.
